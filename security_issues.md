# Аудит уязвимостей проекта (черновик для исправлений)

Дата: 2026-04-04

## Цель
Этот файл фиксирует, что именно небезопасно в текущем состоянии проекта, чтобы потом закрывать пункты по очереди и отмечать прогресс.

## Критично

1. Утечка внутренних ошибок в API-ответах
- Проблема: во многих обработчиках возвращается `error: error.message` клиенту.
- Риск: раскрытие внутренней структуры сервера, Mongo-моделей и логики.
- Что делать: клиенту отдавать только общий текст ошибки, подробности писать только в серверный лог.

2. Нет защиты CSRF
- Проблема: отсутствует явный CSRF-механизм для state-changing запросов.
- Риск: выполнение действий от лица авторизованного пользователя через сторонний сайт.
- Что делать: добавить CSRF-защиту (токен/двойная cookie-стратегия) и ограничить CORS.

3. Открытый CORS по умолчанию
- Проблема: используется `cors()` без ограничений origin.
- Риск: любой origin может вызывать API в браузерном контексте.
- Что делать: разрешить только доверенные домены через переменные окружения.

## Высокий приоритет

4. Слабая генерация `uniqueId`
- Проблема: `Math.random()` для генерации идентификаторов.
- Риск: предсказуемость, перебор ID.
- Что делать: использовать криптографический генератор (`crypto.randomBytes`) или UUID.

5. Слишком большой срок жизни JWT
- Проблема: токен на 7 дней без refresh-потока.
- Риск: длительный доступ при краже токена.
- Что делать: сократить TTL access-токена, добавить refresh-токены и ротацию.

6. Нет дополнительных security headers
- Проблема: отсутствует `helmet` и явные заголовки безопасности.
- Риск: clickjacking, MIME-sniffing, слабая браузерная защита.
- Что делать: подключить `helmet` и корректно настроить CSP/HSTS.

7. Слабая защита auth-эндпоинтов от брутфорса
- Проблема: общий rate limit мягкий, нет отдельного строгого лимита на login/register.
- Риск: перебор паролей.
- Что делать: отдельный лимитер на auth (например, 5-10 попыток / 15 мин на IP + account lockout).

8. Хранение больших файлов в base64 в MongoDB
- Проблема: медиа переводится в data URL/base64 и хранится в документах.
- Риск: рост размера БД, деградация производительности, дорогие запросы.
- Что делать: вынести медиа в объектное хранилище (S3/аналог), в БД хранить URL + метаданные.

## Средний приоритет

9. Избыточные размеры тела запроса
- Проблема: глобальные лимиты JSON/form-data большие.
- Риск: DoS по памяти/CPU.
- Что делать: уменьшить лимиты по умолчанию и задавать точечные лимиты на нужные маршруты.

10. Нет единого слоя валидации входных данных
- Проблема: валидация фрагментарная, не для всех полей и эндпоинтов.
- Риск: некорректные данные, потенциальные векторы атак и логические баги.
- Что делать: ввести централизованную схему валидации (например, zod/joi/express-validator).

11. Потенциальный XSS-риск в пользовательском контенте
- Проблема: комментарии и rich text требуют четкой политики очистки/рендера.
- Риск: XSS при изменении фронтенд-рендера в будущем.
- Что делать: серверная/клиентская санитизация + безопасный рендер HTML.

12. Нет механизма сброса пароля и политики блокировки
- Проблема: нет recovery-процесса и lockout после серии неудачных входов.
- Риск: проблемы с безопасностью и доступностью аккаунтов.
- Что делать: reset flow с одноразовыми токенами + lockout/slowdown.

## Технический долг по наблюдаемости

13. Недостаточный аудит действий админов
- Проблема: критические действия (бан, смена роли, массовые операции) не всегда журналируются отдельной audit-записью.
- Риск: сложно расследовать инциденты.
- Что делать: добавить audit log (кто/что/когда/откуда).

14. Недостаточная стандартизация обработки ошибок
- Проблема: разные форматы ошибок в разных роутерах.
- Риск: сложно централизованно защищать и мониторить API.
- Что делать: единый error-handler middleware + единый контракт ответа.

Шаг 1 (срочно):

- Ужесточить rate limit для auth.

Шаг 2:
- Перевести `uniqueId` на криптогенерацию.
- Пересобрать JWT-схему (access + refresh).
- Снизить глобальные лимиты payload.

Шаг 3:
- Централизованная валидация входа.
- Санитизация пользовательского контента.
- Вынести медиа из MongoDB.

Шаг 4:
- Добавить password reset.
- Добавить lockout/slowdown.
- Добавить audit log и метрики по security-событиям.
